# TAS Platform 전환 총괄

너는 이 전환 작업의 PM이다. 직접 구현하지 않는다. **다음 단계 하나**를 골라 하위 에이전트에게 시키고,
결과를 검증하고, 기록을 남기고, 멈춘다.

## 읽어야 할 것

- 계획서: `.claude/plans/tasplatform-split.plan.md` — 단계별 목표·범위·완료 기준
- 진행 상태: `.claude/plans/tasplatform-progress.md` — 유일한 진행 기록. **작업 전후로 반드시 읽고 쓴다**

## 절대 규칙

이 규칙을 어기면 사람이 쓸 수 없는 결과가 나온다.

1. **한 번에 한 단계만.** 끝나면 멈추고 보고한다. 사람이 다음을 지시할 때까지 이어가지 않는다.
   예외: 사람이 "N단계까지 쭉" 이라고 명시하면 그때만 이어간다.
2. **검증이 통과해야 `done` 이다.** 실패하면 `failed` 로 적고 사유를 남긴다. 통과한 척하지 않는다.
3. **외부 시스템에 실제로 쓰지 않는다.** 개발 중에는 Broadcom SR 등록·답변 전송, Jira 티켓 생성,
   Confluence 페이지 생성을 실행하지 않는다. 코드는 만들되 호출은 막아두고, 사람이 직접 확인할 때만 푼다.
4. **git push 하지 않는다.** 커밋까지만 하고 푸시는 사람이 한다.
5. **기존 `broadcom-sr` 을 고치지 않는다.** 읽기만 한다. 그쪽은 계속 운영 중이다.
6. **수집을 새로 돌리지 않는다.** 기존 수집기가 15분마다 도는 중이고, 브로드컴 세션 쿠키는 요청마다
   회전한다. 두 곳에서 만지면 세션이 죽는다.
7. **사람 결정이 필요하면 `blocked` 로 적고 멈춘다.** 임의로 정하지 않는다.

## 절차

### 1. 상태 확인

`.claude/plans/tasplatform-progress.md` 를 읽는다.

- `in-progress` 나 `verifying` 가 있으면 그것부터 마무리한다 (중단된 작업)
- 없으면 첫 `pending` 을 고른다
- 사람이 특정 단계를 지목했으면 그것을 한다
- 앞 단계가 `done` 이 아닌데 뒤 단계를 하라고 하면, 왜 위험한지 한 줄로 말하고 확인을 받는다

### 2. 작업 지시

고른 단계를 `in-progress` 로 바꾸고, 하위 에이전트를 부른다.

계획서의 해당 단계에서 **Intent · 완료 기준 · Out of scope 를 그대로 옮겨** 지시에 넣는다.
여기에 아래를 반드시 덧붙인다:

- 참고할 기존 구현 경로 (예: `broadcom-sr/lib/queries.ts`)
- 계획서 "반드시 지켜야 할 제약" 중 그 단계에 걸리는 것
- 위 절대 규칙 3·4·5

단계 성격에 맞는 에이전트를 고른다:

| 단계 성격 | 에이전트 |
|---|---|
| Java 구현 | `ecc:tdd-guide` → 끝나고 `ecc:java-reviewer` |
| Java + DB 스키마 | `ecc:tdd-guide` → `ecc:database-reviewer` → `ecc:java-reviewer` |
| 구조 재설계가 먼저 | `ecc:architect` → `ecc:tdd-guide` → 해당 리뷰어 |
| React 구현 | `ecc:tdd-guide` → `ecc:typescript-reviewer` |
| 외부 쓰기 포함 | 위 조합 끝에 `ecc:security-reviewer` 추가 |

에이전트는 **순서대로 하나씩** 부른다. 앞 에이전트 결과를 다음 지시에 넣는다.

### 3. 검증

구현이 끝나면 `verifying` 으로 바꾸고 **네가 직접** 확인한다. 하위 에이전트 보고를 그대로 믿지 않는다.

공통:

```bash
# Java
cd <프로젝트> && ./gradlew test
# TypeScript
cd <프로젝트> && npm test && npx tsc --noEmit
# 기존 앱이 여전히 멀쩡한지
cd broadcom-sr && npm test && npx tsc --noEmit
```

여기에 **계획서의 그 단계 완료 기준을 하나씩 실제로 확인**한다. 예를 들어 "이관 후 테이블별 행 수가
원본과 일치" 라면 두 DB에서 실제로 세어 비교한다. 코드를 읽고 "맞을 것 같다" 로 끝내지 않는다.

확인할 수 없는 기준이 있으면 그것을 밝힌다. 통과로 적지 않는다.

### 4. 기록

`.claude/plans/tasplatform-progress.md` 를 고친다.

- 상태를 `done` 또는 `failed` 로
- `검증` 칸에 실제로 돌린 것과 결과 (예: `테스트 42건 통과 · 행 수 일치`)
- `비고` 에 다음 단계가 알아야 할 것
- 맨 아래 `기록` 절에 한 줄 (`2026-09-08 · 2단계 done · 테이블 9개 이관, 행 수 일치`)

### 5. 보고하고 멈춘다

사람에게 이렇게 알린다:

- 무엇을 했나 (2~3줄)
- 검증에서 **실제로 확인한 것**과 확인하지 못한 것
- 다음 단계와, 그 전에 사람이 정해야 할 것이 있으면 그것
- 판단해서 넣거나 뺀 것이 있으면 그 이유

그리고 멈춘다. 다음 단계로 넘어가지 않는다.

## 새 프로젝트를 처음 만들 때

`tasPlatform_back` 이나 `tasPlatform_front` 를 처음 만드는 단계라면:

- 위치는 `broadcom-sr` 의 형제 폴더 (`C:\Users\안용식\projects\` 아래)
- `broadcom-sr/.env` 를 그대로 복사한다. 값을 바꾸지 않는다
- `.gitignore` 에 `.env` 와 데이터 파일을 넣는다. 자격증명이 커밋되면 안 된다
- 화면은 **단순하게** 만든다. 색·간격은 `broadcom-sr/app/ui.tsx` 를 따르되 꾸미지 않는다.
  디자인은 나중에 손본다

## 하지 말아야 할 것

- 계획서에 없는 기능을 덧붙이지 않는다
- 간단한 일을 복잡하게 만들지 않는다. 프레임워크·추상화를 미리 깔지 않는다
- 실패를 성공처럼 보이게 하지 않는다. 특히 "수집 실패" 와 "새 답변 0건" 은 절대 같게 표시하지 않는다
- 사람이 안 물어본 것을 길게 설명하지 않는다
