# Broadcom SR Hub

## Problem

데이터솔루션 Broadcom 지원팀 5명이 **공유 계정 1개**로 여러 고객사(NH은행, KB생명 등)의 SR을 대행 접수·추적·응대한다. Broadcom 답변이 도착했는지 알려면 팀원이 각자 포털에 로그인해 확인해야 하는데, 세 가지가 겹쳐 이게 잘 안 된다.

1. 포털의 케이스 업데이트 알림이 **공유 계정에 묶인 다른 메일함**으로 가서 팀이 보지 못한다.
2. 동일 계정 **중복 로그인 시 기존 세션이 해제**되어, 확인하러 들어간 사람이 작업 중인 다른 팀원을 밀어낸다.
3. SR 작성과 종료 후 보고서 요약이 매번 수작업이고, 그때마다 포털을 들어가야 한다.

결과적으로 답변 인지가 늦어지고, 팀 내에 "누가 어느 케이스를 보고 있는지" 공유되지 않는다. 방치하면 고객사 대응 지연이 계속 누적된다.

## Evidence

- **사용자 진술(2026-09-02)**: "계속 들어가서 확인해야 함", "알림이 다른 계정으로 가서 보기 힘들고", "우리가 하나씩 들어가서 작성하기 불편", "case 종료 시 보고서 형식으로 요약도 알아서 되면 좋겠다"
- **사용자 진술**: "동일 아이디 중복 로그인하면 접속 해제됨" — 공유 계정 구조에서 오는 구조적 제약이며, 포털 자체 기능으로는 해결되지 않는다
- **실측 조사(2026-09-02)**: 케이스 목록·상세·답변 스레드·첨부 메타데이터가 조회 가능함을 확인. 답변 작성 주체(우리 측 / Broadcom 측)를 구분할 수 있는 필드가 존재함을 확인
- **실측 조사**: 포털 세션은 단명 토큰이며 MFA(OTP) 기반이라 무인 재로그인이 불가능
- **미검증**: 현재 답변 인지까지 걸리는 실제 지연 시간 — `Assumption — needs validation via 운영 2주간 수집 로그와 열람 시각 비교`

## Users

- **Primary**: 데이터솔루션 Broadcom 지원팀 엔지니어 5명. 공유 계정 1개로 로그인하며, 고객사를 대신해 SR을 접수하고 Broadcom 답변을 받아 고객사에 전달한다. 하루 중 수시로 "답변 왔나" 확인이 필요한 상황이 트리거.
- **Not for**:
  - 고객사(NH은행 등) 담당자 — 이 도구에 직접 접근하지 않는다
  - Broadcom 측 엔지니어 — 이 도구의 존재를 알 필요가 없다
  - Broadcom 외 다른 벤더의 지원 티켓 — 범위 밖

## Hypothesis

We believe **팀 공유 SR 대시보드와 답변 도착 웹 푸시 알림**이 **포털 왕복과 계정 세션 경합으로 인한 답변 인지 지연**을 해소할 것이다 — **공유 계정을 쓰는 지원팀 엔지니어 5명**에게.

We'll know we're right when **답변 도착부터 팀이 인지하기까지의 시간 중앙값이 10분 이내로 떨어지고, 팀원이 포털에 직접 로그인하는 횟수가 주 1회 이하로 줄어들 때.**

## Success Metrics

| Metric | Target | How measured |
|---|---|---|
| 답변 인지 지연 (중앙값) | ≤ 10분 | 답변 수집 시각 vs 팀원 최초 열람 시각 |
| 팀원의 포털 직접 로그인 | 주 1회 이하 | 수집 세션이 외부 로그인으로 끊긴 횟수로 간접 측정 |
| 수집 성공률 | ≥ 95% | 수집 로그의 성공/실패 비율 |
| 답변 누락 | 0건 | 포털 실제 케이스 수 vs 수집된 케이스 수 주간 대조 |
| SR 작성 소요 시간 | 현행 대비 50% 단축 | 마일스톤 4 이후 측정 (기준선 먼저 측정 필요) |

## Scope

**MVP** — 읽기 전용. 팀이 포털에 들어가지 않고도 "새 답변이 왔는지"를 알 수 있는 상태까지.

1. 케이스 목록·상세·답변 스레드를 주기적으로 수집해 팀 공용 저장소에 보관
2. 팀원 5명이 웹으로 열람 (목록 → 클릭 → 본문 및 답변 스레드 전문)
3. Broadcom 측 새 답변 도착 시 웹 푸시 알림
4. 수집 로그 페이지 — 마지막 수집 시각, 신규 답변 건수, 세션 상태, 실패 사유

**Out of scope**

- **사람 확인 없는 자동 전송** — 케이스에 올라가는 글은 Broadcom과의 공식 기술 커뮤니케이션 기록이며, 부정확한 자동 응답이 실제 장애 대응을 오도할 수 있다. 모든 전송은 사람 승인 게이트를 거친다
- **케이스 상태 변경·삭제·클로즈 등 조회 외 쓰기** — 마일스톤 4의 답변 등록을 제외한 모든 변경 작업
- **고객사 직접 접근 제공** — 고객사가 이 도구를 보는 시나리오는 다루지 않는다
- **Broadcom 외 벤더 티켓 통합** — 지금 필요 없다
- **모바일 앱** — 웹으로 충분하다

## Open Questions

- [ ] **서버가 없다.** 수집은 단일 인스턴스로만 돌아야 하는데(중복 로그인 = 세션 해제) 24시간 켜둘 장비가 아직 없다. 팀 내 상시 가동 PC 1대로 시작할지, 사내 서버를 요청할지 결정 필요
- [ ] **웹 푸시는 HTTPS 보안 컨텍스트를 요구한다.** `http://내부IP` 접속으로는 브라우저 알림이 동작하지 않는다. 내부 인증서를 쓸지, 대안 알림 방식(탭 내 배너·소리)으로 시작할지 결정 필요
- [ ] **첨부 업로드 경로가 미검증이다.** 다운로드 구조는 확인했으나 업로드는 실제 1회 수행 관찰이 필요하다 — needs validation via 실제 첨부 업로드 1회 캡처
- [ ] **LLM 번역·요약 시 고객사 정보가 외부로 나간다.** 금융권 고객사 시스템 구성이 포함되므로 사내 정보보호 정책 확인이 선행되어야 한다. 불가 시 마일스톤 4·5의 방식을 재설계해야 함
- [ ] **정식 서비스 계정 API 발급 가능 여부.** 포털이 서비스 계정 인증을 받아들이는 정황이 있어 Broadcom에 문의 예정. 발급되면 세션 경합·MFA 재로그인 문제가 모두 사라져 수집 방식을 교체할 수 있다
- [ ] **수집 주기**를 몇 회로 할지 (답변 인지 목표 10분과 낮은 접속 빈도 유지가 상충)
- [ ] **과거 종료 케이스를 어디까지 백필**할지

## Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| 수집기와 팀원의 포털 로그인이 서로 세션을 밀어냄 | High | High | 수집기를 단일 인스턴스로 고정. 팀원이 포털에 들어갈 이유 자체를 없애는 것이 목표. 세션이 끊기면 다음 주기 재시도 |
| 세션 만료를 조용히 실패로 넘겨 "답변 없음"으로 오인 | Medium | High | 수집 실패와 "새 답변 없음"을 절대 같은 상태로 표시하지 않는다. 수집 로그 페이지에 세션 상태를 명시 |
| 공유 계정이라 누가 무엇을 등록했는지 추적 불가 | High | Medium | 도구 내부에 작성자·승인자 기록을 남겨 감사 추적을 확보 (마일스톤 4) |
| 금융권 고객사 정보가 외부 LLM으로 전송됨 | Medium | High | 사내 정보보호 확인을 마일스톤 4 착수 전제 조건으로 둔다. 불가 시 사내 모델 또는 수동 작성으로 전환 |
| MFA 때문에 세션 만료 시 무인 복구 불가 | High | Medium | 만료를 감지해 담당자에게 재로그인 요청. 재로그인 절차를 1분 내 끝나도록 단순화 |
| 포털 UI·API 변경으로 수집이 깨짐 | Medium | Medium | 수집 실패를 즉시 드러내고, 조회 계층을 교체 가능하도록 분리 |
| 승인 게이트를 우회한 오발송 | Low | High | 전송 기능을 사람 승인 없이는 호출 불가능하게 설계. 마일스톤 3까지는 전송 기능 자체를 포함하지 않음 |
| 접속 빈도가 높아 비정상 트래픽으로 인식됨 | Low | Medium | 수집 주기를 낮게 유지. 뷰어는 저장소만 읽고 포털에 접속하지 않음 |
